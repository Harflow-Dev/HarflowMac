## Slice A: feed live append

A new row no longer reloads the whole activity table. `ActivityFeedNativePlan` previously could never return its append case for a real feed, because `build` always ends with a bottom sentinel. It now plans `.tailInsert(removeLeading:insertAt:count:)`, which removes rows that slide out of the 100-row window and inserts new rows before the first trailing entry. Everything else, including a held loading or error header, a regroup and environment or root changes, stays structural. This is shared by task, Parallel and workflow activity.

Order: capture reading if paused, install entries, measure; in a zero-duration animation group, batched remove and insert, then note heights; lay out; one scroll write; refresh every realized changed cell; lay out. The refresh follows the write because rects before the write do not reflect what it brings into view: review found a changed cell scrolled into view stale, which the old full reload had hidden.

Reading: a following reader writes bottom. A paused reader restores if rows were removed, a height changed, or its reading sits in trailing entries, because an insert above a tail or approval pushes it down. A paused reader whose top row slides out clamps to the top with the first surviving row as row 0, because its earlier position cannot be kept. That case needs an unpinned paused state, which arises only transiently, because pausing pins the boundary once it sticks. Clamping together with `maybeLoadOlder` in one reconcile could not be reached through the approval-reveal route, so it is untested with a real load.

Review, three reviewers, two rounds. Opus flagged the stale cell, the runner test and test strength; Codex flagged batched-slide verification; Vibe flagged stale comments and a non-row stand-in. All were accepted. Two round 1 requests changed on evidence: the following-reader stale variant passed before the fix and stays as a guard, and the reachable real-route test uses a mid-feed reading row.

Evidence on final product code, focused runs through the guarded runner: 27 suites including task, Parallel and workflow activity, with no failures; runner tests 137. SwiftFormat reported nothing to format; SwiftLint 0.57.1 reported no violations (CI pins 0.63.2); both guards passed. Strict package gates wait for the end of this stage.

Opt-in synthetic soak, 180 seconds: at most 10 hosts, RSS +2 MB, footprint -10.8 MB, idle 0.002 core, 0.98 falling to 0.90 core while streaming. Before the fix it was RSS +6.9 MB, footprint +1 MB, 0.97 to 0.95 core. This soak streams into one row with a fixed id, so it plans `.unchanged` before and after this slice and exercises neither reloads nor tail inserts: it says nothing about the cost of either. The roughly one core is unexplained and may include the test harness, which rebuilds a 3000-row snapshot and polls on the main actor each tick. It is a named M05 item, to be profiled before this stage closes. Live append is covered by hosted tests for behaviour, not by any CPU measurement. The real-app #34 profile remains open.

## Slice B: `task-changes` client

MonitorCore decodes the `task-changes.v1` listing and text chunks, gated by a fresh capability handshake per command. HfRepository `TaskChangesRepository` reads a listing or one patch. There is no UI and no caller. `EditedFiles` is unrelated and is not a fallback.

- Fail closed: missing or altered attribution, inconsistent pages, repeated cursors, repeated paths within a scope, input after the last page or chunk, oversized documents before any parse, `content.bytes` disagreeing with `total_bytes`, and reported conflict text over the engine's bound. Unknown states stay open values.
- `TaskChangesCompleteness.isComplete` is false for pending, unavailable and not captured states, truncated rows or scopes, and `unmerged_unknown`. `hasNoChanges` additionally needs at least one repository, a null capture reason and no reported conflicts, so "no repository" does not read as "no changes".
- `text_b64` keeps exact bytes. Only incomplete identity fields make a selector non-addressable. Diff text stays out of descriptions, errors, logs and persistence.
- A read is bounded to 64 requests across restarts and a 120 second deadline, checked before each request, so a read can overrun by one in-flight command. Cancelling does not kill a running child. Superseded reads are a typed outcome, not an error.

Changed from the plan: the re-read on pending moves to G2's VM, because it needs the VM's lifetime and `Scheduling`, and the wire states no retry cadence.

Review, three reviewers, two rounds. Opus flagged unbounded work, the silently dropped re-read, `hasNoChanges` semantics, untyped superseded reads and an off-by-one in the conflict size. Codex flagged duplicate rows falsely establishing completeness and the byte bound checked after parsing. Vibe flagged the invented retry cadence and input after the end. All accepted. Rejected: giving a mid-read document change a restart signal, because failing closed is correct and the caller can retry.

Evidence is the 20 vendored fixtures plus labelled synthetic cases, through the guarded runner. It is not exercised against a running engine.
