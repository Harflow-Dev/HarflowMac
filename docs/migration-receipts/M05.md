## Slice A: feed live append

A new row no longer reloads the whole activity table. `ActivityFeedNativePlan` previously could never return its append case for a real feed, because `build` always ends with a bottom sentinel. It now plans `.tailInsert(removeLeading:insertAt:count:)`, which removes rows that slide out of the 100-row window and inserts new rows before the first trailing entry. Everything else, including a held loading or error header, a regroup and environment or root changes, stays structural. This is shared by task, Parallel and workflow activity.

Order: capture reading if paused, install entries, measure; in a zero-duration animation group, batched remove and insert, then note heights; lay out; one scroll write; refresh every realized changed cell; lay out. The refresh follows the write because rects before the write do not reflect what it brings into view: review found a changed cell scrolled into view stale, which the old full reload had hidden.

Reading: a following reader writes bottom. A paused reader restores if rows were removed, a height changed, or its reading sits in trailing entries, because an insert above a tail or approval pushes it down. A paused reader whose top row slides out clamps to the top with the first surviving row as row 0, because its earlier position cannot be kept. That case needs an unpinned paused state, which arises only transiently, because pausing pins the boundary once it sticks. Clamping together with `maybeLoadOlder` in one reconcile could not be reached through the approval-reveal route, so it is untested with a real load.

Review, three reviewers, two rounds. Opus flagged the stale cell, the runner test and test strength; Codex flagged batched-slide verification; Vibe flagged stale comments and a non-row stand-in. All were accepted. Two round 1 requests changed on evidence: the following-reader stale variant passed before the fix and stays as a guard, and the reachable real-route test uses a mid-feed reading row.

Evidence on final product code, focused runs through the guarded runner: 27 suites including task, Parallel and workflow activity, with no failures; runner tests 137. SwiftFormat reported nothing to format; SwiftLint 0.57.1 reported no violations (CI pins 0.63.2); both guards passed. Strict package gates wait for the end of this stage.

Opt-in synthetic soak, 180 seconds: at most 10 hosts, RSS +2 MB, footprint -10.8 MB, idle 0.002 core, 0.98 falling to 0.90 core while streaming. Before the fix it was RSS +6.9 MB, footprint +1 MB, 0.97 to 0.95 core. This soak streams into one row with a fixed id, so it plans `.unchanged` before and after this slice and exercises neither reloads nor tail inserts: it says nothing about the cost of either. The roughly one core is unexplained and may include the test harness, which rebuilds a 3000-row snapshot and polls on the main actor each tick. It is a named M05 item, to be profiled before this stage closes. Live append is covered by hosted tests for behaviour, not by any CPU measurement. The real-app #34 profile remains open.

## Slice B: `task-changes` client

MonitorCore decodes the `task-changes.v1` listing and text chunks, gated by a fresh capability handshake per command. HfRepository `TaskChangesRepository` reads a listing or one patch. There is no UI and no caller. `EditedFiles` is unrelated and is not a fallback.

- Fail closed: missing or altered attribution, inconsistent pages, repeated cursors, repeated paths within a scope, input after the last page or chunk, oversized documents before any parse, `content.bytes` disagreeing with `total_bytes`, and reported conflict text over the engine's bound. Unknown states stay open values.
- `TaskChangesCompleteness.isComplete` is false for pending, unavailable and not captured states, truncated rows or scopes, and `unmerged_unknown`. `hasNoChanges` additionally needs at least one repository, a null capture reason and no reported conflicts, so "no repository" does not read as "no changes".
- `text_b64` keeps exact bytes. Only incomplete identity fields make a selector non-addressable. Diff text stays out of descriptions, errors, logs and persistence.
- A read is bounded to 64 requests across restarts and a 120 second deadline, checked before each request, so a read can overrun by one in-flight command. Cancelling does not kill a running child. Superseded reads are a typed outcome, not an error.

Changed from the plan: the re-read on pending moves to G2's VM, because it needs the VM's lifetime and `Scheduling`, and the wire states no retry cadence.

Review, three reviewers, two rounds. Opus flagged unbounded work, the silently dropped re-read, `hasNoChanges` semantics, untyped superseded reads and an off-by-one in the conflict size. Codex flagged duplicate rows falsely establishing completeness and the byte bound checked after parsing. Vibe flagged the invented retry cadence and input after the end. All accepted. Rejected: giving a mid-read document change a restart signal, because failing closed is correct and the caller can retry.

Evidence is the 20 vendored fixtures plus labelled synthetic cases, through the guarded runner. It is not exercised against a running engine.

## Streaming CPU profile

The named M05 item. Measured with `sample` on the test process (not a hosted suite; `swiftpm-testing-helper`) during opt-in streams of 60 to 180 seconds, in a debug build, with `ActivityFeedStreamingCPUProfileTests` variants. `syspolicyd` and WindowServer were busy throughout, so the machine was not idle. Raw samples and scripts are outside the repository.

| Variant | Cores while streaming | Stream paused, row still live | After finish |
| --- | --- | --- | --- |
| Fixed row, caret animating | 0.91 | 1.02 | 0.002 |
| Fixed row, caret not animating | 0.23 | 0.002 | 0.002 |
| Append, caret animating | 0.97 | 1.02 | 0.002 |
| Append, caret not animating | 0.94 to 0.97 | 0.002 | 0.002 |
| Snapshots prebuilt, no harness preparation | 0.93 | | |

Findings, attributed by call stack in the samples:

- Nearly all CPU is on the main thread. About 58 to 62% of its busy time is SwiftUI sizing the feed's `NSViewRepresentable` through `AppKitPlatformViewHost.fittingSize`, which adds the native table's whole subtree, 75 views and 296 constraints, into a temporary Auto Layout engine.
- `StreamingCaret`'s 30 Hz `TimelineView` drives that path while a row streams: with the caret not animating, CPU falls from 0.91 to 0.23 core and that bucket from 58% to 4%, and with ticks stopped and the caret animating CPU stays at 1.02 core. The sampled chain runs from the cell's `NSHostingView` update through constraint invalidation up to a SwiftUI root transaction and `fittingSize`. The caret's own body costs about nothing. Calls per second were not counted reliably.
- Live append costs about four times the fixed-row tick with the caret not animating (0.94 against 0.23 core), through the same sizing path plus `applyTailInsert` and height flushes. The main thread is saturated, so the true per-append cost may be higher.
- The test harness is about 5%: prebuilding snapshots removes it without lowering CPU.
- Product feed passes over all 3000 shown entries are about 35 ms per tick in the debug build.

Not established: the production rate, since the app was not run; release-build costs; whether the sizing is one call per caret frame or a feedback loop. `ActivityFeedNativeList` implements no `sizeThatFits`, so SwiftUI falls back to `fittingSize`; supplying one, as `StoredRequestText` and `ComposerPromptEditor` do, and a caret animated by Core Animation rather than per-frame view updates, are hypotheses to test, not fixes. The earlier soak figure of about one core is explained: it is this path, not reloads and not the harness.

## Stage G1b: Summary entry and the Events usage group

Design reference: HarflowDesign `17739e4`, the done state's Summary entry (`hd-turn-sep` "Summary", then the prose). Only the standalone mount (`TaskDetailChrome.standalone`) draws it. Group and the workflow builder row are unchanged.

What landed: `ActivityRow.summary(SummaryEntry)`, decided off the main actor in `TaskDetailTimelineBuilder.build` by `TaskDetailSummaryEntryRule.decide` and appended as the last row, with the id `<currentTaskID>#summary`. The summary text comes from `TaskReportedSummary`, the one projection that `recomputeSummary` also uses. `TaskDetailVM` takes an explicit `chrome:` and copies `chrome == .standalone` into `TaskDetailTimelineInput.showsSummaryEntry`. `summaryEntryShown` is part of `TaskDetailTimelinePresentation`, is written to the VM only when it changes, and is cleared when the task goes missing. While it is true, the standalone Events usage group passes `showsHeroAndResult: false`, reads "Reported usage", and keeps its `.usage` identity, expansion and 360 point frame.

Lifecycle notes:

- Every build requires: the current member is the conversation's last, the shown status and that member's snapshot are both `completed`, the projected summary is non-blank, there is no managed-workflow result error, and the frame's `logState` is `final`. A decision already made for the same member, raw summary and observation source is kept as it is, whatever the currentness or drain state (a reconnecting or source-change-pending window, or a drop of `forwardDrained` or `caughtUp`), and its duplicate check is not repeated.
- Establishing a new decision also needs `forwardDrained`, `caughtUp` and `currentness == .current`, none of `unsupportedPayload`, `normalizationLoss`, `skippedRecords`, `gaps` or `ambiguousOrder` in `history.reasons`, and text evidence: with no text item and older history, it waits for paging.
- The duplicate rule compares the raw reported summary with the last `.text` item of any kind in the member's raw projector items, byte for byte; a streaming last text never suppresses. The projected text is what is displayed.
- Decisions are keyed by source: `SummaryEntryDecision.scope` is the frame's `EventObservationScope` (session, source and window ids). A source adoption or window reset changes it, so an old decision is never reused across one, even when the intermediate build was coalesced. No repository change was needed.
- A decided entry is re-made when `logState` is withdrawn or stops being final, the member changes, the raw summary changes or the source changes. A capacity or nonprogress issue (which withhold `logState`), a follow-up member becoming current, or a view disappearing withdraws it.
- A tool-only final turn with older history withholds the entry until the person pages back; the Result stays in Events meanwhile.
- While activity is disabled the frame keeps its last lifecycle; a stale `final` is terminal and harmless.
- First appearance plans `.tailInsert` when that path is eligible (existing rows, matching leading headers, unchanged trailing entries) and is structural otherwise, for example in the build that removes the live-step tail or as the feed's first row. Removal is structural; an anchor on the removed entry falls back to the previous row.

- The usage group heading reads "Reported usage" while the entry shows, a copy deviation pending the D-USAGE ledger classification.
