## M07-A workflow runtime-binding prerequisite — 2026-11-16

This bounded follow-up binds existing Needs you workflow question and recovery
submission to the runtime observation that produced the displayed request. It
adds no visible layout, wording or inline workflow question surface. The existing
approved refusal/changed presentation is reused; this is not a new design approval.

`WorkflowResponseContext` carries the selected runtime token and observation epoch,
separately from approval decision authority. Production derives it from the existing
composition-shared runtime observation. Missing or superseded context refuses a
submission, including A→B→A with copied run/decision IDs. `NeedsYouEngine` forwards
the captured runtime through a narrow `WorkflowRepository.command` overload, which
chains the caller's epoch check onto the bound client's currentness check. The
existing compatibility-probe boundary checks currentness again before launching
the mutation. Existing payload-file lifetime and recovery reporting are preserved.
No dependency callback or publication is introduced under a state lock.

A late completion settles only its original acquisition scope. MainWindow retained
request identity includes the runtime observation and attention checkpoint as well
as the root/source and decision. A replacement request reusing the row ID cannot
inherit the old card, submission state or completion's draft-clearing effect. Drafts
and existing refusals remain available; there is no automatic answer replay.
Runtime observation is not authenticated caller identity. This slice does not add
a general workflow unknown-outcome owner or uncertainty recovery UI, menu direct
question answers, M08 operations, wire contracts, MonitorCore behavior, fixtures,

## M07-B inline workflow questions — local implementation checkpoint, 2026-11-17

Design: approved recording `ee51b74`, visual commit `9093e75`,
`v2/scripts/states-workflow-questions.js`, the four `needs-you/workflow-question*`
states and their minimum variants. Inline workflow questions use independent exact-request
mounts, drafts, errors and submissions under the existing single Needs you VM/subscription.
Approval and recovery rows retain their existing presentation. Inline accepted/winning answers also
populate the existing bounded selected-detail receipt cache after exact completion guards, preserving
deep-link inspection; the selected detail renderer is unchanged.

The inline retention policy is new screen-session behavior: previously displayed receipts,
resolved questions and unreadable-source questions remain inspectable while Needs you is mounted.
Only authoritative current requests contribute to the pending count; a local receipt excludes
only its exact request until absence is observed. A scope transition (including an empty loading
snapshot) and disappearance clear inline state. The existing 32-receipt bound applies to all nonpending inline cards, including winning receipts
with saved drafts. Pending and unreadable-source drafts are never silently evicted. Evicted receipts
leave only a lightweight exact identity while that request is still reported; it suppresses reoffering
that same request and clears on absence, replacement, scope change or disappearance.
There is no timer, dismissal action, automatic answer replay or generic transport-unknown retry.
Draft and action callbacks carry the rendered mount and exact request; completions stay with their
origin and lifecycle. Offered choices remain exact engine tokens, and ownership copy comes from
the existing mapper. Open run routes through the coordinator to the recorded root workflow.

Read-only snapshot workflow context is published from the repository's captured runtime scope,
including empty/loading snapshots. Qualification loss retires that scope before an ordered empty
invalidation. This is observation provenance, not answer authority.

Primary recorded the pre-change guarded fixture baseline: two test definitions/eight cases passed,
