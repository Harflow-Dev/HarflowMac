# M02-B — Xcode project restructure

Date: 2026-11-11 (Asia/Jakarta). Lead: HarflowMac. Follow-up to [M02](M02.md); M02 owner acceptance remains pending.
Status: **implemented and validated locally; owner Xcode check pending.**

## Request and decisions

Owner request (2026-11-10, confirmed 2026-11-11): open the app from the project alone (no wrapper workspace), show every local Swift package as a grouped local folder, and give every package its own scheme and tests, following a reference Xcode project that uses synchronized folders. Decisions: the shell package lives at `macos/HfFeatures/Harflow`; the app scheme is `HarflowHost`; `Harflow.xcworkspace` is deleted; the CI macro-trust failure is out of scope and acceptance is local.

Start commit `98ec18b`; four implementation commits follow (move host files, move shell, synchronized groups, schemes and test plan) and this records commit. The reference survey and the approved plan are kept outside the repository.

## Planning measurements (Xcode 26.6, build 17F113)

A throwaway project showed: packages are discovered only when they sit one level below a synchronized group folder (a group that is itself a package is not); name-only product dependencies link; the synchronized app folder packages icons and images while an `Info.plist` membership exception avoids a duplicate; per-package shared schemes run package tests; an app and a package with the same scheme name list twice (the previous project already did); `Bundle(url:)` on a flat folder holding `Info.plist` and the images finds both menu bar representations.

LaunchServices disclosure: the planning spike used the real `Info.plist`, so its Xcode build registered a scratch app with bundle id `dev.harflow.mac` and the `harflow` URL scheme. That was not covered by M02's permission (only `macos/build/Harflow.app`). It was unregistered and deleted afterwards. Rule since: scratch builds use a unique bundle id and a plist without URL types.

## Resulting layout

- `macos/Harflow.xcodeproj` opened directly; five synchronized groups: `HarflowHost` (app target folder: entry wrapper, `Info.plist` excluded from membership, app icon, menu bar images), `Configuration` (test plan), `HfFoundation`, `HfCore`, `HfFeatures`. No local package references; the target keeps one name-only `Harflow` product dependency.
- Shell package moved to `macos/HfFeatures/Harflow` (manifest paths adjusted, lockfile moves with it); host files moved to `macos/HarflowHost`.
- Ten shared schemes: `HarflowHost` plus one per package. `HarflowHost` defaults to `macos/Configuration/Harflow-UnitTests.xctestplan` and has `buildForTesting` off.
- `build-app.sh` uses `-scheme HarflowHost`; target build settings are unchanged except the plist path.
- `tests/ci/test_app_host.py` now checks host folder contents and plist exclusion, single name-only product link, synchronized roots and one-level package depth, scheme and test plan coverage, no workspace, and that CI covers every package exactly once.

## Hosted suites: measured deviation from the plan

The plan was to skip all `HOSTED_SUITES` (38 MainWindowFeature suites) with per-suite skips. Measured on Xcode 26.6: neither test plan `skippedTests` nor scheme `SkippedTests` removed any Swift Testing suite or function from a SwiftPM test target, in about a dozen identifier spellings (`Suite`, `Target/Suite`, `Suite/`, `Suite/test()`, dotted forms), while the command line `-skip-testing:Target/Suite` works. Two earlier Xcode runs of MainWindowFeature (scheme and plan) therefore ran the hosted suites in Xcode's process; they created UUID-named fixture preference files in the user's Library/Preferences (14 files, removed afterwards). Target-level controls do work (measured): plan `"enabled": false` and scheme `skipped = "YES"`. Final form: the whole `MainWindowFeatureTests` target is disabled in the plan and skipped in the MainWindowFeature scheme, which is a superset of the planned skips; `test_app_host.py` asserts this and that all hosted suites live in that target. The guarded runner (`--mode suites`) is the only route for MainWindowFeature.
